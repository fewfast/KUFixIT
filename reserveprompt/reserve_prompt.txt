ทำงานกับโปรเจกต์ KUFixIT โดยใช้ `progresswork/worklist.txt` และภาพในโฟลเดอร์ `progresswork/` เป็นข้อกำหนดจากเจ้าของโปรเจกต์ ตรวจ AGENTS.md หรือคำแนะนำใน repository ก่อนแก้ไฟล์

เป้าหมายงาน:
1. แก้ UI overflow/error ของหน้า User และ SuperAdmin ตามภาพ `Userfix1.png` และ `Adminfix1.png`
2. ปรับหน้า Admin จัดการช่างให้อ่านง่ายตาม `Adminchange1.png`/`Adminchange2.png` และแสดง 1 ทีม/รายการต่อหน้า
3. ทำ workflow ผลงานช่างหลัง Admin อนุมัติรายงาน รวมถึงการบันทึกผลอุปกรณ์ การจัดการกำหนดซ่อม รูปผล และการนำ ticket ออกจากรายการงานช่าง
4. กรณีช่างซ่อมไม่สำเร็จหรือทำงานไม่ทัน ให้บันทึกผลและ comment ตามข้อกำหนดใน worklist
5. ปรับหน้าติดตามงานซ่อมให้แสดงช่วงเวลาซ่อมครั้งถัดไป และประวัติซ่อมพร้อมรูปผลลัพธ์

ข้อกำหนดก่อนแก้ส่วน backend:
- อ่านส่วนท้ายของ `progresswork/worklist.txt` ให้ครบ และตรวจ schema/migrations/Edge Functions/โค้ดปัจจุบันก่อนออกแบบการบันทึก
- หากยังไม่ได้คำตอบจากเจ้าของโปรเจกต์ ให้ถามทันทีเรื่อง:
  a. คอลัมน์ทั้งหมดในตารางประวัติซ่อม เพราะ worklist ที่ได้รับจบกลางรายการหลัง “ช่วงเวลาซ่อม”
  b. ความหมายของ `false` ใน `fix_history_progress` และสถานะที่ต้องคง/เปลี่ยน เมื่ออุปกรณ์ไม่สำเร็จหรือช่างทำไม่ทัน
  c. ตำแหน่งและชนิดข้อมูลของ `next_fix_date_start`/`next_fix_date_end` เนื่องจากชื่อที่ระบุใน worklist ไม่ตรงกับ schema ที่ตรวจพบก่อนหน้า
  d. ขนาดรูป “จำนวนอุปกรณ์ × 2 MB” ว่าเป็น quota รวมต่อ ticket หรือขนาดสูงสุดต่อรูป และชื่อเลข `1, 2, 3` ใช้แทน index อุปกรณ์หรือหมายเลขรูป
- ห้ามเดาความหมายของข้อมูลหรือแก้ schema ที่มีผลต่อข้อมูลจริงจนได้รับคำตอบ
- ทำงาน UI ที่แยกจากข้อสงสัยเหล่านี้ต่อได้ โดยไม่รอส่วน backend

การทำงานกับผลรายงาน:
- เมื่อ Admin อนุมัติ ให้บันทึกผลใน `fix_history_progress` ของตารางอุปกรณ์ประจำ ticket ตาม index ที่ถูกต้อง
- อุปกรณ์ที่ผลเป็น `true` ต้องถูกเปลี่ยนสถานะเป็น `finish` ตาม worklist
- จัดการค่า `false`, สถานะเดิม, กำหนดซ่อม และการนำ ticket ออกจากตารางช่างตามคำตอบของเจ้าของโปรเจกต์
- กรณีทำไม่ทัน ให้ใช้ comment “ซ่อมไม่สำเร็จ” และบันทึกผลตาม semantics ที่เจ้าของโปรเจกต์ยืนยัน
- จัดเก็บรูปใน bucket `technician-work-results` โดยใช้ prefix/folder ตาม ticket ID ตามรูปแบบของ Supabase Storage และตรวจข้อจำกัดขนาด/การตั้งชื่อจากคำตอบของเจ้าของโปรเจกต์
- การอนุมัติและการเปลี่ยนข้อมูลที่เกี่ยวข้องต้องทำอย่างปลอดภัยและสอดคล้องกัน ไม่ให้สถานะค้างครึ่งทางหาก operation ล้มเหลว

UI:
- แก้ responsive layout ให้ไม่เกิด RenderFlex overflow ในขนาดจอแคบ โดยเฉพาะตารางและคอลัมน์ที่มีข้อความยาว
- หน้าจัดการช่างแสดงทีละ 1 รายการ/ทีมต่อหน้า พร้อม pagination ที่ถูกต้องตามจำนวนข้อมูลจริง
- หน้าติดตามงานแสดงช่วงเวลาเริ่ม–สิ้นสุดในรูปแบบที่เจ้าของโปรเจกต์ยืนยัน
- ประวัติซ่อมแสดงเฉพาะคอลัมน์ที่เจ้าของโปรเจกต์ระบุ พร้อมดูรูปผลการซ่อมได้

ความปลอดภัยและการรักษางานเดิม:
- รักษา RLS และการตรวจ session/role ฝั่ง Edge Function
- ห้ามเปิดสิทธิ์อ่าน/เขียนตารางให้ client เพิ่มเพื่อแก้ปัญหา UI
- ห้ามแสดง secrets, tokens, password hashes หรือข้อมูลส่วนบุคคลใน logs
- ตรวจ `git status` และ diff ก่อนเริ่ม ห้าม revert หรือเขียนทับงานที่ไม่เกี่ยวข้อง
- ห้าม apply migration หรือ deploy production โดยไม่มีการยืนยันจากเจ้าของโปรเจกต์

การตรวจสอบ:
- เพิ่มหรือปรับ tests สำหรับ behavior ที่แก้ และรันการตรวจที่เหมาะสม
- ยืนยันว่า UI ไม่ overflow ที่ขนาดจอที่เกี่ยวข้อง
- ตรวจผลรายงานทั้ง success, failure, timeout และการ rollback/error path
- รายงานผลจริง ห้ามอ้างว่าผ่านหากไม่ได้รัน

การส่งต่องานเมื่อใกล้หมด token:
- ตั้งแต่เริ่มงานให้รักษา checkpoint สั้น ๆ ใน `progresswork/SESSION_HANDOFF.md` โดยบันทึกงานที่เสร็จ ไฟล์ที่แก้ คำสั่ง/ผลตรวจ สิ่งที่ค้าง และคำตอบที่ยังรอจากเจ้าของโปรเจกต์
- เมื่อบริบทหรืองบ token ใกล้หมด ให้หยุดเริ่มงานใหม่ อัปเดต checkpoint และสร้าง prompt ภาษาไทยแบบพร้อมคัดลอกสำหรับ AI ตัวถัดไป
- prompt ส่งต่อต้องระบุเป้าหมายเดิม สถานะจริง ไฟล์สำคัญ สิ่งที่ห้ามทำ ขั้นตอนถัดไป และ tests/verification ที่ยังต้องทำ
- ห้ามสรุปว่างานเสร็จ หากยังมี requirement หรือการตรวจสอบค้างอยู่

เมื่อรายงาน ให้แยก:
1. งานที่ทำเสร็จ
2. งานที่ยังค้าง/ถูกบล็อกและเหตุผล
3. tests และผลตรวจจริง
4. migration/deploy ที่ยังไม่ได้ทำ
5. prompt ส่งต่อ หากยังมีงานเหลือ
